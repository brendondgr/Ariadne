# Conflicting-Evidence (Contradiction) Detection Layer

## 1. Introduction

Ariadne's synthesis verifier (`utils/synthesis/verifier.py`) is excellent at one axis of trust — **groundedness**: every claim must cite a real retrieved record, every asserted id must appear in that record's id pool, and empty specialists must abstain with the executed query as proof. What it does *not* do is the second axis the proposal calls out: **consistency across sources**. When ATT&CK (Neo4j) and CAPEC (Gremlin) both carry a record for the *same* canonical join key yet assert *incompatible* facts about it — a different canonical name, a deprecated-vs-active status, or a mapping that points at a different technique — both records are real, so both survive verification and can appear side by side in the answer with nothing flagging the disagreement. This is why the proposal item "Detects conflicting evidence" was audited **PARTIAL**.

This plan adds a deterministic **reconciliation pass** to the verifier that walks the federation join index, compares corroborating records that share a canonical key against a conservative allow-list of comparable fields, and emits `Conflict` records when they disagree. Conflicts do not fabricate a winner: they surface both asserted values with provenance, mark the affected claims **contested** (kept visible, badged — not silently shown as fact), and roll up a `conflict_count` metric. The front end gains a "Conflicting sources" surface plus a contested badge on affected claims, and a visible "reconcile" ticker step so the analyst sees the check happen. The design stays inside the project's governing principle — *the model drafts, deterministic code grades* — so the contradiction detector is pure, testable, and never trusts the composer it audits.

## 2. Gaps & Unanswered Questions

- **What counts as "incompatible"? (the crux)** A general fuzzy comparator would be noisy. *Assumption*: a conservative, explicit allow-list of comparable fields only — (a) **canonical name** (normalized: case-folded, whitespace-collapsed, punctuation-trimmed; only a *material* difference counts, not "Process Injection" vs "Process injection"), (b) **lifecycle status** (one source marks the entity `deprecated`/`revoked`/`x_mitre_deprecated` while the other treats it as active), and (c) **mapping-target mismatch** (a `correlation` claim's join value resolves to different partner ids across sources). Everything else is ignored to keep false positives near zero. This allow-list is the crux of the feature and is the most likely thing to tune after first data.
- **Cut vs. flag a contested claim?** *Assumption (recommended)*: **flag, do not cut**. Both underlying records are genuinely retrieved, so cutting would hide real evidence; the honest move is to keep the claim rendered but annotate it "contested" with the conflicting values shown. (Contrast: groundedness failures *are* cut, because those cite nothing real.)
- **Should reconciliation pick an authoritative source?** Source cards declare provenance (`source_name`, `id_scheme`). *Assumption*: ATT&CK is authoritative for `Technique`/`SubTechnique` fields (name, status), CAPEC is authoritative for `AttackPattern` fields; when a conflict has a clear authority we annotate which value is authoritative but **still show both**. Whether this authority mapping is correct for every field is a **judgment call — human intervention is welcome to confirm the authority-per-field mapping**, but the feature ships correctly without it (default: surface both, no winner).
- **Interaction with abstentions.** A conflict requires two *present* records; the existing abstention machinery already covers the "one side empty" case. *Assumption*: reconciliation only runs over join values with ≥2 sources present, so it never double-reports an abstention.
- **On-the-wire compatibility.** *Assumption*: `conflicts` is omitted from `to_dict()` when empty so existing event/golden payloads stay byte-identical (same discipline used for `Plan.intent` and `SubQuestion.hop`).

## 3. Hierarchical Step-by-Step Instructions

> **Standing directive (per project memory):** end every step with a **commit + `docs/changelog.jsonl` entry**. Do **not** push — the maintainer's directive overrides the global "push at every step" rule. Where a step touches `web/`, run `npm run build`, `npm run lint`, and `npm test` before committing.

### Step 1: Define the `Conflict` contract and the deterministic reconciler

- **Locations**: `utils/synthesis/contracts.py` (new `Conflict` frozen dataclass: `join_value`, `kind` ∈ `"name"|"status"|"mapping"`, `sources: tuple[str, ...]`, `values: dict[str, str]` source→asserted value, `authoritative_source: str | None`, plus `to_dict`/`from_dict`); new module `utils/synthesis/reconcile.py` housing `detect_conflicts(evidence: FederatedEvidence) -> list[Conflict]`, the field allow-list, the name/status normalizers, and the source-authority table.
- **Rationale**: The comparator is the heart of the feature and must be independently unit-testable before it touches the verifier. Building it as a standalone pure function over `FederatedEvidence.join_index()` (which already maps a join value → the `{source, primary_id, name}` entries carrying it) means it reuses the existing federation spine and the shared `grounding.normalize_id`, and it can be proven correct in isolation. Keeping `Conflict` beside `ClaimVerdict`/`Abstention` matches the existing contract style.
- **Action**: Undergo the verification/tests/validation process for this phase (new unit tests: a name conflict, a status conflict, a mapping conflict, and — critically — a corroborating-but-consistent case that must produce **zero** conflicts). Once validated, commit + changelog stating: Conflicting-Evidence Detection (1/6) Complete: Added the Conflict contract and a standalone deterministic reconciler over the federation join index.

### Step 2: Wire reconciliation into the verifier and annotate contested claims

- **Locations**: `utils/synthesis/verifier.py` (`verify_answer` calls `detect_conflicts` after per-claim verdicts are computed; attaches the result to the report and marks affected claims contested); `utils/synthesis/contracts.py` (`VerificationReport` gains `conflicts: list[Conflict]` + a `conflict_count` property, both threaded through `to_dict`; decide contested-claim representation — recommended: a `contested` flag / reason on `ClaimVerdict` so a contested claim stays `supported` but carries the conflict, keeping `rendered_claims()` showing it).
- **Rationale**: The verifier is the one mandatory, deterministic gate every answer passes through (`verify` is an unconditional edge after `compose`), so it is the correct and only place to guarantee reconciliation runs. Attaching conflicts to the existing `VerificationReport` means they ride the answer payload for free wherever the report already flows. Keeping contested claims `supported`-but-flagged implements the "flag, don't cut" decision from §2.
- **Action**: Undergo the verification/tests/validation process for this phase (extend the verifier tests: a contested claim is still rendered but carries its conflict; `conflict_count` rolls up; a clean answer reports zero and its `to_dict` stays byte-identical). Once validated, commit + changelog stating: Conflicting-Evidence Detection (2/6) Complete: The verifier now reconciles corroborating records and flags contested claims without cutting real evidence.

### Step 3: Confirm the API seam and event/golden payloads carry conflicts

- **Locations**: `api/services/` (the query + conversation renderers that serialize `SynthesizedAnswer` / `answer.synthesis` onto the SSE `answer` event); `api/tests/` and the orchestration/synthesis golden fixtures that assert the answer-event shape.
- **Rationale**: Because `conflicts` is added to `VerificationReport.to_dict`, it propagates through the existing `answer` event automatically — but the golden/event-parity suites pin exact payload shapes, so this step verifies the empty-case byte-identity (omit-when-empty) and adds one populated-case assertion so a regression that drops conflicts on the wire fails loudly. No new endpoint is introduced.
- **Action**: Undergo the verification/tests/validation process for this phase (run `api/tests/` + orchestration goldens; confirm no drift when there are no conflicts, and a new golden covering a conflict-bearing answer). Once validated, commit + changelog stating: Conflicting-Evidence Detection (3/6) Complete: Conflicts serialize through the answer SSE event with empty-case payloads unchanged.

### Step 4: Front-end types + adapter projection

- **Locations**: `web/lib/types.ts` (new `ConflictView` interface; `conflicts: ConflictView[]` on `SynthesisView`; `conflictCount` on the `verification` sub-object; optional `contested` flag on `SynthesisClaimView`/`FlaggedClaimView`); `web/lib/adapt.ts` (`buildSynthesisView` maps `verification.conflicts` → `ConflictView[]` and stamps the contested flag onto affected claims).
- **Rationale**: The workbench renders only from the adapter's UI-ready projection, never raw payloads, so conflicts must be projected here before any component can show them. Making the fields optional/back-compatible keeps older captured payloads (no `conflicts`) rendering unchanged, matching how `edges` and `intent` were introduced.
- **Action**: Undergo the verification/tests/validation process for this phase (`npm test` adapter cases: a conflict payload projects to `ConflictView`s and marks the right claims contested; a conflict-free payload yields an empty list; `npm run lint`, `npm run build`, `tsc` clean). Once validated, commit + changelog stating: Conflicting-Evidence Detection (4/6) Complete: The adapter projects conflicts and contested-claim flags into the UI view model.

### Step 5: Surface conflicts in the workbench (badge + panel + visible step)

- **Locations**: `web/components/center/ClaimTable.tsx` and the prose surface (`ReplyMessage.tsx` / `RefText.tsx`) — a "contested" badge on affected claim rows/sentences; a new `web/components/center/ConflictPanel.tsx` (a "Conflicting sources" section inside the Evidence & Sources / Verified Answers area listing each conflict: the join key, the two sources, both asserted values, and which is authoritative); `web/lib/ticker.ts` (`describeEvent` on the `answer` event adds a "reconcile: N cross-source conflict(s)" line) and, if useful, a phase label in `web/components/center/LiveAnswerStatus.tsx` so reconciliation reads as its own step.
- **Rationale**: The maintainer's standing goal is that every backend decision be legible step-by-step in the UI. A badge makes a contested claim honest at the point of reading; the panel gives the full what/why (which sources, which values, who's authoritative); the ticker line makes the reconciliation *happen visibly* rather than silently. This mirrors the Intent-classification what/why/how surface already shipped.
- **Action**: Undergo the verification/tests/validation process for this phase (`npm test`, `npm run lint`, `npm run build`; verify live in the preview browser that a conflict-bearing answer shows the badge + panel + ticker line, and a clean answer shows none). Once validated, commit + changelog stating: Conflicting-Evidence Detection (5/6) Complete: The workbench badges contested claims, lists conflicting sources, and narrates the reconcile step.

### Step 6: Evaluation metric, docs, and full regression

- **Locations**: `utils/synthesis/` metric surface + the golden/eval report (add `conflict_count` / a conflict-detection check alongside `unsupported_claim_rate`); `docs/synthesis_agent.md` (or the synthesis section of `docs/structure.md`) documenting the reconciliation pass, the allow-list, and the flag-not-cut policy; `docs/planner_agent.md` cross-link if the correlation-intent path is mentioned; `docs/changelog.jsonl`.
- **Rationale**: A capability the proposal is scored on needs a measured number and a documented contract, exactly as intent classification got `intent_accuracy_rate` + `docs/intent-classification.md`. The full regression (with `ORCH_MAX_HOPS=5` to match the committed baseline, per the known `.env` drift) confirms the new layer changes nothing for conflict-free answers and fires correctly when sources disagree.
- **Action**: Undergo the full verification/tests/validation process (entire `utils/` + `api/` pytest, `web` vitest, production build + `tsc`). Once validated, commit + changelog stating: Conflicting-Evidence Detection (6/6) Complete: Added the conflict metric, documented the reconciliation layer, and passed full regression.
