# Plan: Wire the Analyst Workbench to the Live Backend

## 1. Introduction

The Next.js analyst workbench under `web/` is currently a fully static front end: it renders one hand-authored fixture run (`web/lib/fixtures.ts`) and animates it with a hard-coded timer (`web/lib/runMachine.ts`). None of the real Ariadne capabilities are reachable from the browser — there is no network layer, no API routes, and no `fetch` anywhere. Meanwhile every real capability lives in Python and is exposed only through `main.py`'s CLI: live-source health (`--graph health`), the federated question pipeline (`--query` → `PlanningAgent.plan` → `SpecialistRouter.run_plan`), LLM/connection configuration (env vars consumed by `PlannerConfig`/`SpecialistConfig`), and infrastructure control (`--docker`, `--graph`, `--download`, `--build`).

This plan introduces a thin **FastAPI service layer** (new top-level `api/` package) that wraps the existing `utils/` modules without duplicating their logic, and rewires the front end to consume it. Next.js proxies `/api/*` to the FastAPI process (same-origin, no CORS), and the root `app.py` launches both processes together. The chat's "sequence of events" is delivered as **coarse, real Server-Sent-Events** at the boundaries the synchronous pipeline actually exposes (probe → plan → querying → per-specialist → evidence → done); the existing event-driven `runMachine` is repurposed to advance on those real events instead of a timer, and the fine-grained micro-step choreography is driven from the *real* `plan.trace` and `SpecialistResult.traces[]` data already returned by the backend. Three user-facing capabilities are the priority — see whether Neo4j and Gremlin are live, ask questions and watch the staged answer build, and configure the LLM from the app — with the remaining `main.py` actions exposed as a secondary control surface.

## 2. Gaps & Unanswered Questions

- **The pipeline is synchronous and emits no prose answer.** `PlanningAgent.plan()` and `SpecialistRouter.run_plan()` are blocking and return complete `to_dict()` bundles; they emit *evidence* (per-source grounded `summary` strings + normalized records + a join index), never a synthesized paragraph. *Assumption*: the answer card is composed **deterministically on the server** from the grounded per-source summaries + cross-source join values (no fabrication, no extra LLM call). True token-streaming of a prose answer is out of scope because the backend produces none. This is reversible later if a synthesis agent is added.
- **Streaming granularity.** The pipeline cannot stream sub-stage progress; the only real boundaries are "planning finished" and "federation finished." *Assumption*: emit real SSE events at those boundaries plus a per-`SpecialistResult` event, and let the client animate the intermediate micro-steps from the returned `trace`/`traces` arrays. This is genuinely event-driven (the events are real) while preserving the rich staged animation.
- **Config changes vs. a warm process.** Writing to `.env` does not, by itself, change `os.environ` in a running process, and configs are read via `from_env()`. *Assumption*: the config `PUT` endpoint both persists via `utils.config.set_env_values()` **and** updates `os.environ`, and the query endpoint builds `PlannerConfig`/`SpecialistConfig` fresh per request, so edits take effect on the next question without a restart.
- **LLM auth.** The current `OpenAICompatibleDrafter` sends no API key and hard-codes `temperature=0`. *Assumption*: the settings form exposes exactly the env-backed knobs that exist today (`*_LLM_ENABLED`, `*_LLM_BASE_URL`, `*_LLM_MODEL`, `*_LLM_TIMEOUT_S`, `*_LLM_MAX_TOKENS`). An optional API-key field requires a backend code change and is **not** introduced unless a later step explicitly adds it.
- **Long-running infra actions (`--download`, `--build`, `--docker start`).** These take minutes and depend on the host (network, Docker daemon). *Assumption*: they are exposed as triggerable actions that stream log output; success is host-dependent and surfaced honestly in the UI rather than assumed.
- **Process ports.** *Assumption*: FastAPI on `127.0.0.1:8000` (override `ARIADNE_API_PORT`), Next.js on `3000`; Next rewrites `/api/*` → the API port. No new infra. This is a simple gap resolved by assumption.
- **Commit/push policy.** The repo's global rule says "commit AND push." The **user has explicitly overridden this for this session: commit at every step, do NOT push.** Every step below therefore ends with a *local commit only*; the merge to `main` at the end is also local (not pushed). Human confirmation already given — no further intervention needed.

## 3. Hierarchical Step-by-Step Instructions

> Work happens in the git worktree `.claude/worktrees/wire-frontend-backend` (branch `wire-frontend-backend`), branched from local `main` HEAD (local `main` is ahead of `origin/main`, so the worktree must branch from HEAD to contain the front end). Each phase appends a `docs/changelog.jsonl` entry and runs the webfront build when web files change.

### Step 1: FastAPI service scaffold + live-source health
- **Locations**: new `api/__init__.py`, `api/main.py` (the `FastAPI` app + router include + `/api/health`), `api/models.py` (Pydantic response models: `LiveSourceModel`, `HealthResponse`, `DockerStatusModel`), `api/services/health.py` (no-raise wrapper around `utils.graph_loader.main.run_graph_health` + per-store `healthcheck()` + node counts where cheap, and `utils.infrastructure.docker_status`); `pyproject.toml` (add `fastapi`, `uvicorn[standard]`); new `api/tests/test_health.py`.
- **Rationale**: Everything else depends on a running service and a stable JSON contract. Health is the simplest real capability and the first user-visible goal ("is Neo4j/Gremlin live"). `run_graph_health` raises `ConnectionError` when a backend is down, so the service must catch it and return a per-backend `{backend,status,nodes?,reason?}` shape that matches the existing `LiveSource` TS type — turning an exception into structured "down" status.
- **Action**: Undergo the verification/tests/validation process for this phase (`uv run python -m pytest api/tests/ -q` — assert correct shape with backends both reachable and unreachable; confirm no unhandled raise). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (1/8) Complete: FastAPI scaffold and /api/health live-source endpoint.`

### Step 2: Configuration endpoints (view + edit LLM settings)
- **Locations**: `api/models.py` (`ConfigResponse`, `ConfigUpdateRequest` covering planner+specialist LLM fields and read-only connection summary), `api/services/config.py` (read current values from `PlannerConfig.from_env()`/`SpecialistConfig.from_env()`; write via `utils.config.set_env_values()` and mirror into `os.environ`; redact `NEO4J_PASSWORD`), `api/main.py` (`GET /api/config`, `PUT /api/config`), `.env.example` (document the `PLANNER_LLM_*`/`SPECIALIST_LLM_*` keys that today are defaults-only); new `api/tests/test_config.py`.
- **Rationale**: The user must change LLM settings "directly within the app." `set_env_values()` already persists while preserving file layout/comments; mirroring into `os.environ` makes edits live for the next query without a restart. Validation/redaction prevents writing junk or leaking the DB password.
- **Action**: Undergo the verification/tests/validation process for this phase (pytest: GET returns all knobs with password redacted; PUT round-trips to a temp `.env` and updates `os.environ`; invalid types rejected). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (2/8) Complete: /api/config view and edit for LLM settings.`

### Step 3: Federated query endpoint with real SSE staging
- **Locations**: `api/models.py` (SSE event envelope types), `api/services/query.py` (build `PlanningAgent` + `SpecialistRouter` per request from fresh configs; run the blocking calls in a worker thread; yield ordered events — `probe`, `plan`, `query_started`, one `specialist` per `SpecialistResult`, `evidence`, `answer` (server-composed deterministic prose from summaries+joins), `done`/`error`; honor `mode=plan|query` and `drafter=deterministic|llm`), `api/main.py` (`POST /api/query` returning `text/event-stream` via `StreamingResponse`); new `api/tests/test_query.py`.
- **Rationale**: This is the heart of "the sequence of events when we ask a question." Running the synchronous pipeline in a worker thread lets the endpoint emit real boundary events as each stage completes, and reuse the exact `to_dict()` payloads the TS types already mirror. Composing the answer server-side from grounded summaries keeps the answer honest (no model invented prose) while giving the chat something to reveal.
- **Action**: Undergo the verification/tests/validation process for this phase (pytest with an injected stub pipeline: assert event order and each event's JSON shape; assert the backends-down path yields a well-formed `no_sources` stream rather than a 500). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (3/8) Complete: /api/query SSE pipeline with real stage events.`

### Step 4: Front-end data layer — API client + backend→view adapter
- **Locations**: new `web/lib/api.ts` (typed `getHealth`, `getConfig`, `putConfig`, and a `streamQuery` SSE helper), new `web/lib/adapt.ts` (`buildRun({plan, evidence, liveSources}) → WorkbenchRun` plus incremental builders used as events arrive), `web/lib/types.ts` (add SSE event types + any missing fields), `web/next.config.ts` (`rewrites()` proxying `/api/*` → `http://127.0.0.1:${API_PORT}`); new `web/lib/__tests__/adapt.test.ts`.
- **Rationale**: The front end's invariant is "components stay unchanged; only the data origin changes." A single adapter from the backend `to_dict()` shapes to the existing `WorkbenchRun` view-model is the clean seam. Proxying via Next rewrites keeps the browser same-origin so no CORS or absolute URLs are needed.
- **Action**: Undergo the verification/tests/validation process for this phase (`cd web && npm test` — feed the existing federated fixture bundle through `buildRun` and assert it reproduces a `WorkbenchRun` equivalent to `wmiCapecRun`; `npm run lint`; `npm run build`). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (4/8) Complete: web API client, SSE helper, and backend→view adapter.`

### Step 5: Event-driven run lifecycle + live Composer
- **Locations**: `web/lib/runMachine.ts` (replace the `REPLAY_FRAMES` timer with a reducer that consumes SSE events from `streamQuery`, advances `liveStatus`, and accumulates the `WorkbenchRun` via the incremental adapter; keep the fixture as the idle/demo state and a reduced-motion-friendly fallback), `web/components/workbench/WorkbenchContext.tsx` (hold the active run + submit action), `web/components/center/Composer.tsx` (bind textarea value/onChange, mode + drafter toggles, and wire Send → submit), `web/components/center/ChatThread.tsx`/`AnswerCard.tsx` (render the live/in-progress run; skeleton until the `answer` event).
- **Rationale**: This delivers the conversational flow and the staged reveal on real events, satisfying "an animated event-based approach" against live data while leaving the Motion variants and component props untouched. The Composer is currently inert; this is where it becomes interactive.
- **Action**: Undergo the verification/tests/validation process for this phase (`npm run build`/`lint`; with the API running, submit a question and verify via the preview tools that stages advance probe→plan→specialists→evidence→answer, the skeleton resolves on the `answer` event, and the backends-down case shows a graceful `no_sources` turn — no console errors). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (5/8) Complete: event-driven run machine and interactive composer.`

### Step 6: Live infrastructure status + LLM settings UI
- **Locations**: `web/components/header/InfraStatusPill.tsx` (poll `getHealth` on an interval; reflect real live/down/starting with the existing StatusDot animation), new `web/components/settings/SettingsPanel.tsx` (+ a modal/drawer shell) wired to `getConfig`/`putConfig` for the LLM form, new `web/components/settings/Neo4jCredentialsForm.tsx` (URI/user/password → config write), `web/components/header/HeaderBar.tsx` (wire the currently-inert gear/user button to open the panel), `web/components/workbench/WorkbenchContext.tsx` (settings open state).
- **Rationale**: Closes the two remaining priority goals — a live "is it up?" indicator and an in-app settings form for the env-backed LLM knobs — reusing the design system primitives so it stays on-brand and accessible.
- **Action**: Undergo the verification/tests/validation process for this phase (`npm run build`/`lint`; preview: pill flips to live/down against the real `/api/health`; opening settings loads current values, saving persists and re-reads). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (6/8) Complete: live infra status pill and in-app LLM/credentials settings.`

### Step 7: Infrastructure control actions (remaining main.py capabilities)
- **Locations**: `api/services/infra.py` + `api/main.py` (`POST /api/docker` start/stop/status, `POST /api/graph` load/verify/health, `POST /api/data` download/build, `POST /api/neo4j-login`; long-running ones stream logs over SSE), new `web/components/settings/InfraActions.tsx` (buttons + streamed-log drawer, with clear host-dependency notices); `api/tests/test_infra.py` (status/dispatch with subprocess/docker calls stubbed).
- **Rationale**: Fulfills "incorporate every single thing main.py can do." These are administrative, host-dependent operations, so they live in the settings/admin surface and stream their output rather than pretending to be instantaneous.
- **Action**: Undergo the verification/tests/validation process for this phase (pytest with infra calls mocked; `npm run build`/`lint`; preview: trigger `docker status`/`graph health` and confirm streamed output renders). Once validated, **commit locally (do NOT push)**: `Frontend↔Backend (7/8) Complete: infra control endpoints and admin UI.`

### Step 8: Unified launcher, docs, full regression, merge to main
- **Locations**: `app.py` (launch uvicorn for `api.main:app` and the Next.js server concurrently; forward Ctrl+C/shutdown to both; keep existing flags + `--api-port`), `docs/structure.md` + `docs/skills/global-project-rules/SKILL.md` + `docs/skills/website-architecture/SKILL.md` (document the `api/` service, the proxy, and new commands), `docs/changelog.jsonl` (final entry), `README`/usage notes if present.
- **Rationale**: `app.py` must "run everything needed for the web server"; with a backend now required, it has to start both. Docs must reflect the new two-process architecture so future agents don't reintroduce the static-only assumption.
- **Action**: Undergo the full regression for the whole feature (`uv run python -m pytest api/tests/`; `cd web && npm test && npm run lint && npm run build`; boot `python app.py` and confirm `/api/health` 200 + the page renders and can submit a question end-to-end). Once validated, **commit locally (do NOT push)**, then merge the worktree into `main` with `--no-ff` (resolving any conflicts, re-running the regression on `main`): `Frontend↔Backend (8/8) Complete: unified app.py launcher, docs, regression, merged to main.`
